component matrix is in [COMPATIBILITY.md](../COMPATIBILITY.md).

The candidate includes the Teams Files window and batched settings. Microsoft Teams and Google
Chat live campaigns remain on hold pending execution or an explicit deferral.

## Upgrade notes for operators

- The update that brings 0.7.0 rebuilds the runtime image once (the Containerfile and image spec
  1.6.4 changed, and the new `cg.image.bundle` label is absent on older images). After a manual
  `git pull`, run `npm run build:image`.
- On existing system-service installs, run `sudo bash scripts/repair-service-unit.sh` once on the
  gateway host so channel containers survive service restarts. The repair takes effect without a restart.
- If the deployment uses connected mailboxes, turn on **Settings → Email accounts (IMAP/SMTP)**
  after upgrading. The switch defaults to off and existing account data is retained.
- Approval links minted in the 30 minutes before the upgrade restart show "not valid" (approval
  tokens are now signed with a per-purpose derived key); the approval cards in the conversation
  still work.
- `POST /api/runs` with only the admin session cookie now needs the same `X-CG-Request` header as
  every other cookie-authenticated change; API-key and `cgk_` token callers are unaffected.
- Microsoft Teams: an inbound activity whose token has no `serviceurl` claim, or with no
  `serviceUrl`, is refused (Microsoft's SDK rule). Graph subscription validation is answered only
  while this daemon is creating a subscription.
- Host skills: a symlink inside a skill folder that points outside that skill is skipped with a
  warning on import and materialization.
- `/sudo` threads: each gateway tool call confirms with the daemon that the run is still live and
  is refused if the daemon cannot answer.
- Teams settings save per section with Apply to channel / Apply to thread instead of on each field.

- [ ] Full coverage suite and static checks pass on the candidate.
- [ ] Tracked and candidate-history secret scans pass.
- [ ] Dedicated security coverage and high/critical production dependency audit pass.
- [ ] Every candidate commit passes the stable-range DCO check.
- [ ] Candidate CI and documentation checks pass.
- [ ] Active executable private QA cases are inventoried with their Claude/Codex matrix,
      current-candidate results, precise evidence, unresolved defects and approved holds.
- [ ] Human-only cases have an explicit owner and reproducible handoff; assignment is not a pass.
- [ ] Upgrade, backup/restore and rollback prerequisites are checked for the target deployment.
- [ ] An organization admin approves the exact tested candidate after reviewing the evidence
      and explicitly deciding any remaining live-case deferrals.

No tag, main merge, customer update or published release is performed by this preparation.
After approval, retain the previous release/runtime snapshot through the rollback window,
promote only the approved SHA, and keep beta aligned with stable history. For a tagged release,
create the exact package-version tag on main and run the release-evidence workflow. Independently
verify its image inventory, model records, archive, checksums and attestations before distribution.
Unsigned local build metadata is not signed release provenance.

Historical release evidence is retained in [RELEASE-ACCEPTANCE.md](../RELEASE-ACCEPTANCE.md)
and [RELEASE-CHECKLIST.md](../RELEASE-CHECKLIST.md); it is not relabeled for this candidate.
