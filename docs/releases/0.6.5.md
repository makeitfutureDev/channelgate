# 0.6.5 stable promotion candidate

Prepared 2026-11-06. Status: **not approved for stable promotion**.

The promotion PR head identifies the exact candidate. Freeze that SHA in the PR and the private
acceptance manifest after the Sunday cron fix lands. Later beta commits are excluded unless
reviewed, retested and explicitly included in a replacement candidate. This record is a preparation
contract, not a claim that the checks below have run.

## Scope

Promote the integrated beta history since stable, including channel-to-channel agent messages,
Enterprise organization controls and channel spending limits, skill model selection and publication
recovery, email sign-in, SSH destination approval and status bars, Claude usage accounting,
queued Slack forks, runtime recovery fixes and the Sunday `7` cron alias correction.

The runtime requires **Node.js 24.0.0 or newer**. Upgrade the host before updating an older
installation. Runtime image spec is **1.6.3**; rebuild the image for the pinned toolchain and Make
CLI, then verify the actual image/container generation before live acceptance. The full supported
component matrix is in [COMPATIBILITY.md](../COMPATIBILITY.md).

Unmerged Teams settings batching and Files dialog work is excluded. Microsoft Teams and Google
Chat live campaign holds remain in force. Existing integrated transport fixes remain part of the
source candidate; a hold does not mark their acceptance as passed.

## Evidence required before promotion

- [ ] Exact candidate SHA and source range recorded in the promotion PR.
- [ ] Full coverage suite and static checks pass on the candidate.
- [ ] Tracked and candidate-history secret scans pass.
- [ ] Dedicated security coverage and high/critical production dependency audit pass.
- [ ] Every candidate commit passes the stable-range DCO check.
- [ ] Candidate CI and documentation checks pass.
- [ ] Active executable private QA cases are inventoried with their Claude/Codex matrix,
      current-candidate results, precise evidence, unresolved defects and approved holds.
- [ ] Human-only cases have an explicit owner and reproducible handoff; assignment is not a pass.
- [ ] Upgrade, backup/restore and rollback prerequisites are checked for the target deployment.
- [ ] An organization admin approves the exact tested candidate after reviewing the evidence
      and explicitly deciding any remaining live-case deferrals.

No tag, main merge, customer update or published release is performed by this preparation.
After approval, retain the previous release/runtime snapshot through the rollback window,
promote only the approved SHA, and keep beta aligned with stable history. For a tagged release,
create the exact package-version tag on main and run the release-evidence workflow. Independently
verify its image inventory, model records, archive, checksums and attestations before distribution.
Unsigned local build metadata is not signed release provenance.

Historical release evidence is retained in [RELEASE-ACCEPTANCE.md](../RELEASE-ACCEPTANCE.md)
and [RELEASE-CHECKLIST.md](../RELEASE-CHECKLIST.md); it is not relabeled for this candidate.
